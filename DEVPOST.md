# STOW — Devpost Submission Copy

## Tagline

Know what you own. Buy only what you need.

## Short description

STOW is a personal inventory and purchase-decision assistant that helps people avoid duplicate purchases, understand what they already own, and restock essentials at the right time.

## Inspiration

The idea began with a simple, familiar problem: buying a piece of clothing and later realizing that something very similar was already in the wardrobe. The same problem appears in other parts of daily life. People forget what they own, buy duplicates, and notice that household essentials have run out only when they need them.

Most inventory apps answer only one question: “What do I have?” We wanted to connect that record to two more useful decisions: “Should I buy this?” and “What should I restock?”

That became STOW: one clear place to understand what you own and make more deliberate purchases.

## What it does

STOW provides three connected workflows:

1. **Inventory** — users can add, edit, delete, search, and filter personal items.
2. **Purchase Check** — users describe something they are considering, and STOW compares it with their existing inventory.
3. **Restock** — users set an individual stock threshold for each item and see a focused queue when quantities become low.

Purchase Check is intentionally explainable. Instead of returning an unexplained AI percentage, STOW shows a weighted feature breakdown:

- Category: 30%
- Color: 30%
- Style: 15%
- Material: 15%
- Purpose: 10%

The closest existing item, total similarity score, recommendation, and reason are shown together. A 100% match clearly explains why the user should use what they already own before buying another.

## How we built it

STOW uses a three-service Docker Compose architecture:

- **React and Vite** for the frontend
- **Python and FastAPI** for the REST API and recommendation logic
- **PostgreSQL** for persistent inventory and evaluation data
- **SQLAlchemy** for data models
- **Alembic** for database migrations
- **Pytest** for API and similarity tests

The frontend communicates with FastAPI through REST endpoints. Inventory data is stored in PostgreSQL, while the similarity service compares a purchase candidate against every inventory item and returns the highest-scoring match.

We developed the project through feature branches, focused commits, pull requests, reviews, and merges. This gave us a visible development history and helped us verify each feature before it reached the main branch.

## Challenges we ran into

One challenge was keeping recommendations useful without making them feel arbitrary. A single score generated by a black box would be difficult for users—and judges—to trust. We solved this by separating product features from the scoring system and displaying every weighted contribution.

Another challenge was coordinating frontend, backend, and database changes while keeping the app easy to run. Docker Compose gave every contributor the same environment, although we also learned how to diagnose port conflicts caused by older containers.

We also redesigned the original interface after recognizing that the competition audience was international. The final product is fully English and uses a restrained editorial design instead of a generic dashboard aesthetic.

## Accomplishments that we're proud of

- Built a working full-stack product rather than a static prototype
- Created an explainable purchase recommendation with a visible score breakdown
- Connected inventory CRUD, search, filtering, purchase decisions, and restocking
- Added per-item restock thresholds without complicating the user workflow
- Created a reproducible Docker environment for all three services
- Completed a fully English product redesign for an international audience
- Passed all seven backend tests covering CRUD, validation, API behavior, and recommendation bands

## What we learned

We learned that explainability is part of product design, not only model design. Showing why two items match makes the recommendation more actionable and trustworthy.

We also learned how small architecture decisions affect collaboration. Database migrations, environment examples, feature branches, pull requests, and automated tests made it possible to build the project in clear, reviewable stages.

Finally, we learned to test the product as a real user. Several improvements—from English copy to the restock quick action—came from running the complete workflow rather than reviewing individual files in isolation.

## What's next for STOW

The current MVP uses deterministic feature matching so its decisions remain transparent. Next, we plan to add:

- Image-assisted item recognition and automatic feature tagging
- Optional LLM-generated explanations based on verified similarity results
- Usage history and predicted depletion dates
- Authentication and separate inventories for multiple users
- Shopping-list integration
- Deployment and a dedicated mobile experience

## Built with

React, Vite, JavaScript, Python, FastAPI, PostgreSQL, SQLAlchemy, Alembic, Pytest, Docker, and Docker Compose.

## Suggested demo flow

1. Open the Inventory dashboard and show the existing item.
2. Add or edit an item and point out its features and restock threshold.
3. Open Purchase Check and enter a matching product.
4. Show the 100% score and explain the five weighted contributions.
5. Lower the inventory quantity to the restock threshold.
6. Open Restock and use **+ Add one**.
7. Show the **All Clear** state when the item leaves the queue.
